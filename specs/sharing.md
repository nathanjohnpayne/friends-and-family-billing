# Sharing

Covers share link generation, token validation, the share link dialog, and the public-facing share view for family members.

## Approved money projection (#629)

[ADR 0010](../docs/adr/0010-household-cent-projection.md) owns exact household component inputs, cent authority, deterministic projected row allocation and public money-version compatibility. Every money formula below uses those projected integer-cent components; source eligibility and existing invoice/Charge Notice scope remain unchanged. Household totals never sum rounded per-member displays (#620). The explicit money version is required on cache **and** Function responses: missing/old/unknown versions resolve through the compatible Function before any financial totals render, or produce a recoverable unavailable state. A pre-change tab can rewrite an old cache after self-healing; test that race and reject the rewritten cache again. Carried-item presence and background refresh are insufficient. Both public writers and actual response/cache consumers must agree before the Functions-first, Hosting-second release; see [the rollout gates](../plans/629-cent-rounding-rollout.md).

Under the [owner's source-boundary decision](https://github.com/nathanjohnpayne/friends-and-family-billing/issues/633#issuecomment-6690912942), every admitted source money field must be an actual finite JavaScript Number (`typeof value === 'number' && Number.isFinite(value)`). Numeric strings, `NaN`, infinities, `null`, `undefined` and booleans cause an integrity hold for the affected household only; do not publish coerced or partial money totals for it. Internal hold evidence names household, record id, field and observed type. Keep existing presence signals and scope/privacy rules; this decision does not authorize exposing private hold evidence in public payloads. Before M3/M4 start, define their hold rendering and public response contract; the unused M2a adapter chooses neither. Source recorders keep existing write-time parsing, corrections use the app to write Numbers, and no stored conversion or migration is authorized. The [rollout inventory and gates](../plans/629-cent-rounding-rollout.md#source-sign-and-domain-guard-inventory) govern sign/domain exclusions, removal of coerced-money tests during M2b, and M5's non-conforming-field hold counts by component and record ids without authorizing a live read.

## Acceptance Criteria

### Share Helpers

- `buildShareScopes` always includes `summary:read`, `paymentMethods:read`, `usageCharges:read` (#317 — a member always sees their own pending charges on their share, so the scope is on every normal link), and `payments:read` (#356 — a member's payment history is their own data, the same posture as `usageCharges:read`); adds `disputes:create` and/or `disputes:read` when the respective flags are true; and adds `refunds:read` when the third flag is true (#319). The 2-argument dispute call stays backwards-compatible. Links minted before `payments:read` existed simply won't carry it, so the share page degrades gracefully (omits payment history).
- `buildPublicShareData` includes the member's `pendingCharges` (via `buildPendingChargesForShare`) in the generated `publicShares` document when the scopes carry `usageCharges:read`, so the member-facing view is reachable directly from a normally-generated link (not only via the Cloud Function self-heal on a cache miss). It accepts an optional `owedAdjustments` array for this. The React path threads `owedAdjustments` through every share-generation caller (`ShareLinkService`, the ShareLink/Email/Text dialogs, and `InvoicingTab`) for cache-hit consumer parity with the Cloud Function fallback.
- The same `owedAdjustments` array drives the member-facing **owed** (#321 + #322): `buildPublicShareData` composes the household's `combinedAnnualTotal` (and therefore `combinedMonthlyTotal` and `balanceRemaining`) as `max(0, G − S + O)` in integer cents (ADR 0010), where `serviceCreditTotal` is the sum of active `service_credit` adjustments for the primary plus linked members and `openingBalance` is the household's netted carried opening balance — the signed sum of `carry_opening` seed records (a carried **credit** is negative and lowers owed, a carried **charge** positive and raises it) for the primary plus linked members, via `getHouseholdOpeningBalance`. The combined result is floored at 0, mirroring `getHouseholdFinancials` and the invoice so the public share summary agrees with the settlement board. Voided credits/seeds and the `+owed` Usage Charge direction are excluded; billed Usage Charges (#320) are not added here. `carry_opening` is a distinct `kind`, so the service-credit sum ignores it (no double-count). The Cloud Function `resolveShareToken` — the cache-miss / stale-refresh fallback that self-heals `publicShares` — applies the same floored `service_credit` reduction **and** carried-opening-balance adjustment to its `paymentSummary` (via the `getServiceCreditTotalForMember` and `getHouseholdOpeningBalance` helpers in `functions/billing.js`), so the React and Cloud Function member-facing totals agree and the self-healed doc never persists an uncarried (or gross) total.
- `buildPendingChargesForShare` returns the token member's OWN deferred Usage Charges (per-member grain, ADR 0005 — "a linked member sees their own pending charges"; the household grain is only for the admin settlement board) as `{ charges, total, count }`: only `kind: 'usage_charge'` records with `status: 'deferred'` whose `memberId` is the token member are included; voided/billed charges and other members' charges (including linked household members) are excluded; charges are sorted by incurred date ascending and each carries a `runningTotal`; only member-safe fields (`id`, `description`, `amount`, `incurredDate`, `runningTotal`) are exposed; an unknown member or empty input yields an empty result.
- `buildPaymentHistoryForShare` (#356) returns the household's (the token member plus their linked members — the same grain as `totalPaid`) settled payments as member-safe line items: `{ payments: [{ id, date, amount, method }], count }`, newest first. Only "live" ledger entries are projected — reversal entries (`type: 'reversal'`) and reversed originals (`reversed === true`) are excluded, so their allocated cents sum to the projected household `P` (exact original/reversal pairs net to zero under ADR 0010). Only member-safe fields are exposed (`id`, `date` = the payment's `receivedAt`, `amount`, `method`); the free-text `note` is never included. `buildPublicShareData` includes `paymentHistory` in the generated `publicShares` document when the scopes carry `payments:read`, and the Cloud Function `resolveShareToken` mirrors the same field (via the `functions/billing.js` mirror) into both its response and the self-healed doc, so the cache-hit, cache-miss, and self-healed doc all agree (an explicit cache↔CF parity test asserts the two builders produce identical output). The history allocates projected `P` to eligible live rows under ADR 0010; it does not independently recompute financial authority or change stored ledger values.
- `buildCarriedItemsForShare` (ADR 0009, `specs/year-end-review.md` § Member-facing surfaces) returns the household's itemized opening balance as `{ fromYear, notApplied, remainingCredit, items: [{ memberId, memberName, kind, basis, billName, description, amount, detail }], total }` from the primary's and linked members' `carry_opening` seeds: one signed line per carried True-up share, member charge, or household credit (the credit's `detail[]` is explanatory, never added), `total` equal to projected net opening `O` (ADR 0010), only member-safe fields, nothing from other households. A seed without `items` yields one line `{ kind: 'legacy', description: 'Carried from <year>', amount }`. `buildPublicShareData` includes it as `carriedItems` under `summary:read` when the total is non-zero or any item exists, and the Cloud Function `resolveShareToken` mirrors the same field through `functions/billing.js` into both its response and the self-healed doc (reconciled with `FieldValue.delete()` when absent, like `serviceCredits`), with an explicit cache↔CF parity test; the function ships before the client renders the section. Two numbers are kept apart: `notApplied = max(0, −(billsSubtotal − serviceCreditTotal + total))`, the household's floor remainder shown by the "Not applied this year" row (it includes any Service Credit excess, which the rollover forfeits), and `remainingCredit`, the unused incoming credit the rollover carries and the only amount the "$Y remains" sentence states, computed from the net `total` exactly as the rollover computes `U`: `I = max(0, −total)`, `Q = max(0, total)`, `A = max(0, billsSubtotal − serviceCreditTotal + Q)`, `remainingCredit = max(0, I − A)`; the seed's charge/credit split never enters it, so a +$10.00 charge and −$10.00 credit under a Service Credit excess show nothing remaining (`specs/year-end-review.md` § Member-facing surfaces and § Itemized carry define both the same way; fixtures 10l and 10n).
- `buildServiceCreditsForShare` returns the household's active Service Credits (#337) as member-safe line items for the share summary: `{ items: [{ reason, billName, amount }], total }`. Active `service_credit` records for the primary plus linked members are aggregated by (billId + reason) so a bill-level split (one record per affected member) shows as a single line; the `+owed` Usage Charge direction, voided credits, `carry_opening` seeds, and other members' credits are excluded; only member-safe fields are exposed. The `total` is projected `S`, already folded into `combinedAnnualTotal`; group rows receive ADR 0010 largest-remainder cents by the deterministic constituent-record identity, so two $0.005 groups total $0.01, not $0.02. `buildPublicShareData` includes `serviceCredits` in the generated `publicShares` document under `summary:read` when the total is positive, and the Cloud Function `resolveShareToken` mirrors the same field (via the `functions/billing.js` mirror) so the cache-hit, cache-miss, and self-healed doc all agree.
- `buildShareTokenDoc` includes rawToken when truthy and omits it when null (invoice flow); sets defaults for revoked (false), lastAccessedAt (null), accessCount (0).
- `buildShareUrl` constructs a URL in the format `{origin}/share.html?token={token}`.
- `computeExpiryDate` returns null for 0, null, or negative days; returns a future Date for positive days.
- `isShareTokenStale` returns true for revoked tokens, true for expired tokens, false for non-expired non-revoked tokens, false when no expiry is set, and correctly handles Firestore Timestamp-like objects with `.toDate()`.

### ShareLinkDialog Component

- Renders the "Generate & Copy Link" tab by default.
- Opens the manage tab when `initialTab="manage"`.
- Shows link expiry and scope options (e.g., "Allow member to request bill reviews") on the generate tab.
- Renders nothing when not open.
- Shows both "New Link" and "Manage Links" tab buttons.

### ShareView (Public-Facing)

- Shows "No share token provided" error when no token is in the URL.
- On a compatible-money-version publicShares cache hit: renders member name heading, year pill, and bumps access count via updateDoc.
- On cache miss with successful Cloud Function response: renders data from the response and sends the correct POST payload to `/resolveShareToken`.
- On cache miss with failed response: shows the server error message or a generic "invalid or has been removed" fallback.
- On network/unexpected error: shows "Could not connect" message.
- Bills section renders bill names, monthly amounts, annual shares, split counts, member count labels, and a TOTAL row.
- "Request Review" buttons appear when scopes include `disputes:create`; hidden when they do not.
- Dispute form validates empty messages (shows error styling), clears error on typing, calls `addDoc` with correct fields (memberId, memberName, billId, billName, message, proposedCorrection, status, createdAt, tokenHash) on submit, and shows a success message.
- Cancel button closes the dispute form overlay.
- Payment summary section shows annual total, monthly total, paid to date, balance remaining, percentage paid, outstanding balance callout when balance > 0, and settled callout when balance is 0 with payments.
- Evidence viewing: opens `window.open` directly when evidence has a downloadUrl; fetches via `/getEvidenceUrl` when no downloadUrl, showing "Loading..." while fetching.
- Dispute approval/rejection: shows Approve/Reject buttons when `userReview.state` is "requested"; clicking Approve calls updateDoc and shows "You approved this resolution."; hides buttons when state is "approved_by_user" or "rejected_by_user".
- Payment methods section renders method labels, handles, and Copy buttons; hidden when empty.
- Payment history section (#357) renders the household's settled payments from the `payments:read` payload (`paymentHistory`, built by `buildPaymentHistoryForShare`) behind a collapsed "Show payment history ({count})" entry point that expands to a date / method / amount list (method via `getPaymentMethodLabel`, amount via `formatCurrency`). Only member-safe fields are shown — never the free-text note. The section degrades gracefully: it is omitted entirely when the resolved data carries no `paymentHistory` (older links that predate `payments:read`) or an empty list.
- Disputes section renders dispute details (bill name, status, message, resolution note); hidden when empty.
- Pending charges (deferred Usage Charges, #317) render as a compact amber **notice** (mockup redesign) placed right after the bill/summary (not at the bottom of the page): a "{count} upcoming charge(s) — not yet due" header, one line per charge (amount · description · incurred date), and a total — only when the resolved share data carries a non-empty `pendingCharges` (which the Cloud Function returns only for the `usageCharges:read` scope); hidden when the scope is absent or there are no deferred charges. The notice states both dispositions of a pending charge — it will either be billed separately by the admin (the off-cycle Charge Notice path, #320) or applied to the member's bill next year (the carry-forward seam, #322) (#338).
- **Carried from &lt;year&gt;** (ADR 0009): when the resolved data carries `carriedItems`, the page renders the itemized breakdown headed "Carried from 2026" directly under the household total reconciliation, as an expandable panel that is open by default and is toggled by the reconciliation row's amount and by the lead sentence's "carried from &lt;year&gt;" link: lines grouped by member (a linked member's lines under that member), the household credit with its detail lines at the household level, and a "Carried total" line; the household total reconciliation shows the carried total as its own line, and "Other adjustments" then holds only the residual that remains after that line (the `max(0, …)` floor remainder, if any), so the opening balance is never shown twice. Copy follows `specs/year-end-review.md` § Member-facing copy and never says True-up, carry_opening, or adjustment. A legacy seed renders one "Carried from 2026: +$30.00" line. Hidden when there are no carried items.
- Service credits reconciliation (#337): when the resolved data carries `serviceCredits`, the Household's Annual Billing Summary renders a reconciliation under the household total — the bills subtotal, each Service Credit as a `-$amount` line (`Service credit — {billName} ({reason})`), a **Carried from &lt;year&gt;** line for the opening balance (signed; with `carriedItems` present the amount toggles the itemized breakdown rendered directly beneath the reconciliation, open by default; a legacy seed shows the one line), a **Not applied this year** line for the floor remainder when the credits and the carried credit exceed the bills (positive), never the label "Other adjustments" (ADR 0009 member-facing terminology), and the resulting Household Total — so the reduced annual total is explained rather than silently lower than the sum of the bills. Hidden when there are no active service credits.
- Trust banner renders a "secure annual billing summary" notice.
- Shows loading message initially while data is being fetched.

### Refund Notices on the Share Page (#319)

- When the token carries `refunds:read` and the resolved data includes `refundNotices`, a "Your Refunds" section renders each notice with its amount, payment method, and reason; the section is hidden when there are no notices.
- A pending notice (no `confirmation`) shows two actions: **Confirm Receipt** and **I Have Not Received It**. Clicking either POSTs `{ token, noticeId, outcome }` to `/submitRefundConfirmation` (`outcome` is `confirm` or `not_received`)—never a direct Firestore write.
- After confirming, the card shows "You confirmed you received this refund." and the action buttons are removed; after reporting non-receipt, it shows the "reported … as not received" message. A notice that already carries a `confirmation` seeds that terminal state on load (no action buttons).
- If the `/submitRefundConfirmation` POST fails, the card surfaces the server (or a generic) error message and leaves the action buttons in place so the member can retry; the error clears on the next attempt.
- **Live resolution:** because Refund Notices are dynamic (mutable confirmation state) and are NOT stored in the `publicShares` cache — and a freshly issued confirm link is minted before its notice document exists — a `refunds:read` link always resolves live via `resolveShareToken` even on a cache hit. Only dedicated refund-confirm links carry `refunds:read`, so normal share links keep using the cache.
- **Routing:** `/submitRefundConfirmation` is registered as a Hosting rewrite in `firebase.json` (before the SPA catch-all), alongside the other share Cloud Functions, so the member POST reaches the function in deployed Hosting.
- `resolveShareToken`'s `disputes:read` projection excludes `kind: 'refund_notice'` documents (mirroring `useDisputes`), so a normal review-enabled link never renders Refund Notices as empty Review Requests (ADR 0002).

### RefundNoticeService (issuance)

- `issueRefundNotice` mints a `refunds:read` share link (also granting `summary:read`) for the confirm CTA, writes a `refund_notice` doc into the `disputes` subcollection with a server `createdAt`, the snapshot fields, a null `confirmation`, the `creditAdjustmentId`, and the link's `tokenHash`, then emails the member the reason, amount, method, and confirm link.
- The notice persists even when the member has no email (no email sent), when the email send fails (best-effort), or when minting the share link fails (the notice is written without a `tokenHash` and the email goes out without the share URL). Returns the new `noticeId` and `shareUrl`.
