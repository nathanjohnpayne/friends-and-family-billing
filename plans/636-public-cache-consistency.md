## Consistency gap and owner decision

At audited main `bfcf9bb38f55a9339496af04c10f926894d71465`, the resolver separately reads the year and notices, then self-heals without awaiting the write (`functions/index.js:178–190,319–331,408–410`). The rebuild transaction reads token/cache but receives financial inputs from outside that transaction (`src/lib/ShareLinkService.js:163–207`). Year close, notice resolution and member report commit without cache invalidation (`BillingYearService.js:373–416`, `useRefundNotices.js:64–71`, `functions/index.js:1075–1115`). Queued year replacement is not cross-tab coordination (`BillingYearService.js:313–326`; `SaveQueue.js:36–50`). There is no current financial-disposition cancellation writer; notice resolution `type: cancelled` is not that financial event.

A stale marker plus an asynchronous observer cannot guarantee B's next-resolve behavior: a request can arrive before observation, and an older writer can overwrite the marker. Google documents that [Firestore triggers can arrive out of order and more than once](https://firebase.google.com/docs/functions/firestore-events#limitations). This excludes an observer alone as the correctness boundary.

**Recommend owner approval of server admission for every monetary cache read**, using private certification and transactional source reads/publication below. This adds server latency, read cost and contention to ordinary cache hits. It implements **logical invalidation at admission**, not physical fanout at the source commit. Existing owner/old-client writes can still replace public caches; replaced payloads fail admission. Approving that distinction requires an explicit bounded amendment to B/C. Existing ordinary one-hour refresh timing remains, anchored to private certified projection time.

If B instead requires physical invalidation atomically with every source transition, the alternative is a durable household/year fence and atomic participation by every relevant source writer, enforced by rules. Per-token enumeration alone misses newly minted links; asynchronous repair cannot substitute. That alternative expands stored metadata, rules and source mutation orchestration, including legacy queued year replacements and future cancellation writers. Invalidating on every year/credit-array edit would broaden cache timing and needs approval too. It requires another design/split; do not treat it as already authorized.

## Recommended mechanism, pending approval

### Private certificate and targeted dependencies

Propose a new Admin-only collection `shareCacheAdmissions/{tokenHash}` with `{ protocol, ownerId, billingYearId, memberId, dependenciesDigest, payloadDigest, projectedAt }`. It contains no financial authority and is never sufficient without the live token. Missing, expired or revoked token always refuses resolution, even if a certificate/cache remains. Certificate cleanup is not a validity backstop.

The local rules' unmatched-path denial covers this proposed collection (`firestore.rules`, final recursive match); no rules change is proposed. Implementation must prove authenticated and unauthenticated get/list/create/update/delete denial in the emulator. Source inspection does not prove deployed rules. This separate location prevents forged certificate fields on client-created or preexisting tokens; token client permissions remain unchanged. There is no new secret, source mutation endpoint or billing-year Admin write.

Keep certificates, digests, source ids and provenance out of publicShares, responses and logs. PublicShares is publicly gettable; a public signed/hash field is not the proposed trust boundary. The private dependency digest binds owner/year/token-member/actual household membership and only B's targeted dependencies: canonical report states restricted to household notices whose confirmation is `not_received` (notice identity, linked disposition/member identities and resolution presence); cancelled disposition identities; and active versus read-only year mode. Those report states are tracked even while held or read-only, so reports/resolutions invalidate despite null effective reopening. Unreported or confirmed notice additions and unrelated notice amount/text/method edits do not change this guard and must not trigger immediate money refresh; include a fixture proving that exclusion. Eligibility still uses the board's existing helper. Do not use whole-year update time or ordinary bill/payment edits as new immediate-refresh triggers.

The payload digest binds the complete canonical **monetary** envelope: identity, scopes, expiry/validity, version/state and every present/absent scoped money field, including rows and optional money sections. Explicit independent exclusions are `paymentMethods` (including existing `hasQrCode` flags), view metrics (`accessCount`, `lastAccessedAt`) and cache transport timestamp `updatedAt`; the separately stored public QR presentation remains outside this certificate. Existing payment-method synchronization (`src/lib/paymentMethodsSync.js:41–69`) may change those presentation fields without invalidating certified money or resetting private `projectedAt`. Independently validate excluded presentation shape and current scope before use; malformed/unauthorized methods cannot enable payment actions or force an ordinary-money refresh. While unavailable, suppress payment methods/QR actions regardless of later presentation sync. No monetary field may be excluded under this rule, and hashing only totals is insufficient. Clients cannot certify their own replacement monetary envelope.

### One admission/publication transaction

1. Before rendering money, the upgraded client calls the existing resolver. It performs no separate cache access-count increment. Cache presence, compatible version and certificate existence alone never establish admission.
2. In one Admin read-write transaction, read live token, full year, complete Refund Notice query, current cache and private certificate; all reads precede writes. Derive household/status and the five arrays from that year. A successful empty query is ready context; missing/failed context is never empty. Internal household notice reads occur regardless of disclosure scope; detailed notices remain token-member-scoped, `refunds:read` only and live-only.
3. Validate token, cache protocol/state/shape, full monetary-envelope digest and current targeted dependencies; separately validate independent presentation fields and scope. A valid unchanged cache no older than one hour may retain its prior money snapshot. Checking dependencies now does not make that snapshot a newly computed current projection. Admission/metrics/old-client timestamps never reset private `projectedAt`.
4. Preserve stale-then-background refresh after one hour. Apply background unavailable responses immediately under C. Dependency mismatch, absent/invalid certificate or payload, existing refunds:read live requirement, and Try again force a new projection. Try again reads sources; it repairs no year and retries no money write.
5. A forced projection calls `projectHouseholdMoney` once over that transaction's complete source/context snapshot and serializes the public allowlist. All amounts/rows derive from that result. Unavailable removes stale optional monetary keys and retains independent authorized history. Atomically publish cache plus matching private certificate and visit metrics; await commit before replying. Transaction callbacks have no email/audit/HTTP side effects.

Google documents [serializable transactions at commit time](https://firebase.google.com/docs/firestore/transaction-data-contention#serializable_isolation_by_commit_time) and the [Admin transaction query API](https://docs.cloud.google.com/nodejs/docs/reference/firestore/latest/firestore/transaction). This design relies on those transaction semantics, not an observer's delivery order. The installed SDK and real query shape still need regression coverage, including a newly inserted matching notice during projection; no source read outside the transaction may stand in for that context.

### Races, failures and preserved boundaries

- A transition committed before admission is observed or causes retry; the next supported-client resolve goes live on dependency mismatch. A resolver committed first represents the earlier serializable snapshot. Network delivery can arrive later; the same-view successful report must start an authoritative reread and reject older request generations.
- A legacy/client writer may physically replace cache after certification. The next admission rejects a changed payload digest or incompatible shape. It cannot update the Admin-only certificate. If physical writer exclusion is required, that is the alternative's rules/publication redesign, not a claim made here.
- Concurrent visits/background/legacy metric increments conflict on the cache and retry, preserving the existing cache count rather than reseeding from older token counters. One committed visit request increments once; transaction retries and background refresh add none. HTTP retries retain existing non-idempotent behavior; no new exactly-once receipt store is proposed.
- Failed source reads, retry exhaustion or cache/certificate commit failure return recoverable failure without stale-money fallback. A lost handler response after a committed transition does not defeat the next dependency check. Missing notice context never becomes zero. Receipt/report and Review reply remain usable while money is held.
- Required exclusion fixture: a payment-method-only update (including `hasQrCode`/public QR presentation), or metrics/transport-timestamp-only update, preserves certified monetary age and existing visit-count semantics, causes no immediate ordinary-money projection, and never restores held payment/QR controls.
- Ordinary money updates retain existing cache-age behavior; real current-source projection is required only on forced/live refresh. No new cancellation feature, #651 transport recovery, migration, normalization or financial-source write is included.
- [#492](https://github.com/nathanjohnpayne/friends-and-family-billing/issues/492) remains separate: raw publicShares get bypassing expiry/revocation is unfixed. This recommendation governs supported upgraded UI admission; old clients and direct public-document reads are not repaired. Functions-first/old-client behavior remains a separately verified release gate.
