## Chosen consistency boundary

Every upgraded public-money visit goes through `resolveShareToken`. Logical invalidation at admission replaces handler-side cache invalidation: the first admission after a committed report, resolution, disposition cancellation or close detects the targeted change and projects fresh money regardless of cache age. Report, resolution and year-close handlers need no cache knowledge, token enumeration, markers or observers. The physical atomic-fence alternative is not authorized; there is no fallback to it.

The audited implementation at main `bfcf9bb38f55a9339496af04c10f926894d71465` separately reads year/notices and self-heals asynchronously (`functions/index.js:178–190,319–331,408–410`); rebuild transactions receive financial inputs externally (`ShareLinkService.js:163–207`). A marker/observer would leave stale-read and late-writer windows. Google documents [unordered, at-least-once trigger delivery](https://firebase.google.com/docs/functions/firestore-events#limitations), [transaction serializability at commit time](https://firebase.google.com/docs/firestore/transaction-data-contention#serializable_isolation_by_commit_time), and [Admin transaction query reads](https://docs.cloud.google.com/nodejs/docs/reference/firestore/latest/firestore/transaction). The installed runtime/query shape still requires concurrency regressions, including a newly inserted matching notice.

Admission adds server latency/read cost and bounded contention to every upgraded visit. Within one hour, matching dependencies can reuse only a certified **available** money snapshot despite ordinary source edits; checking dependencies now does not turn it into a newly computed projection. **Older than one hour means recompute and publish in the same request transaction**, returning current money. Certified **unavailable** is never reusable: every admission source-projects again regardless of matching guard or young age, so an ordinary source correction is visible on the next visit. No stale-then-background path remains; stop and raise any reason to retain one.

## Certificate and digests

`shareCacheAdmissions/{tokenHash}` is a new Admin-only private collection containing `{ protocol, ownerId, billingYearId, memberId, dependenciesDigest, payloadDigest, projectedAt }`. Existing unmatched-path rules deny client access; implementation must prove owner-authenticated and unauthenticated get/list/create/update/delete denial in the emulator. No rules change is proposed or approved, and deployed rules are not inferred from source. Client-created token metadata cannot certify anything. Missing/expired/revoked live token always refuses, regardless of cache or orphan certificate. Certificate cleanup has an explicit result and is never a validity backstop.

Nothing from the certificate, including private `projectedAt`, enters a response, public cache or log. There is no public digest/signature/provenance field, new secret, source mutation endpoint, year-document Admin write or receipt store.

[ADR 0010](../docs/adr/0010-household-cent-projection.md#public-cache-admission-protocol-671) defines SHA-256 canonicalization with sorted keys, explicit present/absent handling and no float reformatting. The protocol constant is included in **both** digests, so protocol changes invalidate certificates.

- **Dependencies:** bind owner/year/token member/household membership; canonical report states only for household notices with confirmation `not_received` (notice/link/member identity and resolution presence); cancelled disposition identities; active versus read-only year mode. Track reports/resolutions while held/read-only even when effective reopening is null. Reopened eligibility still uses the board's existing helper. Unreported/confirmed notice additions and unrelated amount/text/method edits do not force refresh. Do not use whole-year revision or ordinary bill/payment changes as new immediate-refresh triggers.
- **Payload:** bind every monetary field/row/optional section, present and absent, plus identity, scopes, validity, version and state. The exclusions are **exactly** `paymentMethods` (including `hasQrCode`), `accessCount`, `lastAccessedAt` and `updatedAt`; an added exclusion requires an owner decision. Independently validate payment-method shape/scope and gate held payment/QR controls. Existing separate public QR storage is not certificate data. Payment-method/metrics-only changes do not reset private age or force ordinary-money projection.

### Client monetary writes: pre-code binding gate

For upgraded clients the client writer's exact money payload is a parity artifact for the release interval and owner-side previews. Decision A's one-projection/identical-cents contract still applies. **The first upgraded visit after any client-created or client-rebuilt monetary cache must project on the server**, not certify supplied amounts without recomputation.

A digest detects changed content, not an identical monetary rewrite. Existing private certification can still match if a client rewrites identical included fields while only excluded timestamps/metrics differ. Neither document update time alone (metrics change it too) nor the approved content digest proves the required first-visit rule. Do not claim otherwise. Before #674/#675 source work, resolve this within the permitted protocol or raise the concrete conflict to the owner. A candidate is for every upgraded-client monetary persistence to deliberately remove a required existing compatibility field while retaining the exact compatible serializer as the parity artifact; this is **not selected here**. It requires explicit owner approval to narrow Decision A's persistence-version rule: the pure serializer would remain version 1 with identical cents, while only upgraded-client monetary persistence would clear existing `moneyProjectionVersion`; metrics/presentation updates would leave it untouched. No new nonce, public id/provenance, private-certificate access, rules change or extra transaction write is chosen; those privacy/protocol boundaries remain reserved. An identical rewrite regression is mandatory, alongside changed legacy replacement and presentation-only exclusions.

**Required discriminating fixture:** certify G=$100/P=$100 (10,000/10,000 cents, B=R=0) at t0. Within one hour, an ordinary source edit changes P to $200 (20,000 cents), with the targeted dependency guard unchanged. A stale client then rewrites the complete monetary envelope byte-identically to the certified G=$100/P=$100 payload. Its digest still matches, yet condition 6 requires the next upgraded admission to project current P=$200 and balance −$100, not reuse P=$100. Without that client monetary write, ordinary within-hour reuse could legitimately retain the old snapshot. A changed `updatedAt` or metric cannot prove a monetary rewrite: all are excluded, and existing payment-method-only synchronization also changes `updatedAt` (`paymentMethodsSync.js:59–62`). Test both cases together. Architecture #671 stays approved; only this narrow binding clarification remains decision-needed before source work.


## Exact transaction and response contract

1. After #676 the upgraded ShareView **never reads publicShares directly**, including retry/fallback paths; it renders only admission responses. Remove the raw cache read, separate client metric increment and `refreshOnly` together. Every committed admission increments once; callback retries add none. HTTP retries keep current non-idempotent behavior.
2. Read **exactly** live token, year, complete household notice query, cache and private certificate in one Admin transaction, all before writes. Source household/status/five arrays come from that year. Successful empty notice query is ready; failed/missing context is never empty. Internal notices are read regardless of detail scope; details remain token-member scoped, `refunds:read` only and live-only.
3. Validate live token, protocol/state/shape, both digests and age, independently checking presentation scope/shape. Certified unavailable, missing/invalid certification, targeted mismatch, age over one hour, client monetary write, existing refunds:read live requirement or Try again forces a single fresh `projectHouseholdMoney` result over that snapshot. Never mix cached components into it.
4. Write **only** publicShares and shareCacheAdmissions, including the visit metric update in the cache. Never write token/year. Publish compatible available/unavailable, remove stale optional money, preserve existing cached counts rather than reseeding from token, and preserve actual token validity/scopes. No email/audit/HTTP/logging side effect occurs inside the callback. Await commit before response; read/commit exhaustion returns recoverable failure without stale fallback.
5. Unavailable withholds all money/pay/QR/question/progress/pending output while retaining independent scoped historical notices/actions and Review status/reply. After a successful report the same view starts an authoritative reread and rejects earlier response generations. Required sequence within one hour: hold → report → admission recertifies unavailable with reported history → ordinary invalid-amount correction with targeted guard unchanged → a new visit, without Try again, source-projects available money with reopened eligibility. The young unavailable certificate cannot be reused. Try again performs source reread, not year repair or a money-write retry.

A source transition committed first is observed or causes retry; a resolver committed first represents the earlier serializable snapshot. Network delivery can arrive after later events, hence component generation rejection. A changed/incompatible legacy replacement cannot certify itself. Concurrent admissions/legacy metric writes conflict on cache and retry; certificate/cache remain paired atomically. Existing payment-method sync preserves age/count behavior and cannot restore held controls.
