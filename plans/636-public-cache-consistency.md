## Chosen consistency boundary

Every upgraded public-money visit goes through `resolveShareToken`. Logical invalidation at admission replaces handler-side cache invalidation: the first admission after a committed report, resolution, disposition cancellation or close detects the changed canonical source/context inputs and projects fresh money regardless of cache age. Report, resolution and year-close handlers need no cache knowledge, token enumeration, markers or observers. The physical atomic-fence alternative is not authorized; there is no fallback to it.

The audited implementation at main `bfcf9bb38f55a9339496af04c10f926894d71465` separately reads year/notices and self-heals asynchronously (`functions/index.js:178–190,319–331,408–410`); rebuild transactions receive financial inputs externally (`ShareLinkService.js:163–207`). A marker/observer would leave stale-read and late-writer windows. Google documents [unordered, at-least-once trigger delivery](https://firebase.google.com/docs/functions/firestore-events#limitations), [transaction serializability at commit time](https://firebase.google.com/docs/firestore/transaction-data-contention#serializable_isolation_by_commit_time), and [Admin transaction query reads](https://docs.cloud.google.com/nodejs/docs/reference/firestore/latest/firestore/transaction). The installed runtime/query shape still requires concurrency regressions, including a newly inserted matching notice.

Admission adds server latency/read cost and bounded contention to every upgraded visit. A private validated-source digest covers everything the canonical authority consumes. **Changed source inputs call `projectHouseholdMoney` once and publish/serve that result: unavailable or fresh available money.** Do not validate current sources then discard a valid result to return old money, and do not update only a validation memo. `projectHouseholdMoney` remains the sole held/valid authority; the digest is an equality fingerprint, not a second financial validator.

Within one hour only unchanged canonical source/context inputs, matching payload/certificate and certified **available** state may reuse the snapshot without monetary projection or certificate rewrite. The required one-visit metric update still occurs. Over one hour the same transaction recomputes/publishes and returns current money. Certified unavailable always reprojects, and invalid/missing certification, envelope mismatch/incompatibility, refunds:read's live rule and Try again still force projection. This deliberately tightens the earlier one-hour policy: changed ordinary financial sources now publish current money immediately. No stale/background path remains.

## Certificate and digests

`shareCacheAdmissions/{tokenHash}` is a new Admin-only private collection containing `{ protocol, ownerId, billingYearId, memberId, sourceDigest, payloadDigest, projectedAt }`. Existing unmatched-path rules deny client access; implementation must prove owner-authenticated and unauthenticated get/list/create/update/delete denial in the emulator. No rules change is proposed or approved, and deployed rules are not inferred from source. Client-created token metadata cannot certify anything. Missing/expired/revoked live token always refuses, regardless of cache or orphan certificate. Certificate cleanup has an explicit result and is never a validity backstop.

Nothing from the certificate, including private `projectedAt`, enters a response, public cache or log. There is no public digest/signature/provenance field, new secret, source mutation endpoint, year-document Admin write or receipt store.

[ADR 0010](../docs/adr/0010-household-cent-projection.md#public-cache-admission-protocol-671) defines SHA-256 canonicalization with sorted keys, explicit present/absent handling and no float reformatting. The protocol constant is included in **both** digests, so protocol changes invalidate certificates.

- **Validated source:** `sourceDigest` covers the complete canonical raw input representation consumed by `projectHouseholdMoney`, including the five raw arrays, authority-consumed financial/eligibility settings, year status, household argument/membership, allocation identities/order/denominators, eligibility/status and every source/shape/type/value distinction relevant to any canonical hold class, plus the options/detail context and year/notice eligibility inputs. Payment-method-only presentation settings are excluded from validation input; do not blindly hash the whole presentation settings object. Preserve invalid values and their type distinctions in a lossless typed canonical encoding; do not coerce, normalize or erase them while fingerprinting (for example NaN/infinity/undefined must not collapse to JSON null/absence). If safe fingerprinting fails, invoke the canonical projection and fail closed rather than admit a partial digest; any inability to publish a safe certificate returns recoverable failure without stale fallback. Fingerprinting cannot decide which malformed input is held. The implementation inventory must prove every authority-consumed input is included; no sampled fields, separate amount-only checker or whole-year timestamp shortcut. Include report/resolution, cancelled dispositions, household binding and active/read-only context even while held/read-only so B's transitions remain covered. Reuse the board helper. Former targeted dependencies are subsumed; no separate dependency digest is needed. Payment-method/metric/transport-only presentation and notice text/method fields not consumed by authority/eligibility do not become financial refresh triggers.
- **Payload:** bind every monetary field/row/optional section, present and absent, plus identity, scopes, validity, version and state. The exclusions are **exactly** `paymentMethods` (including `hasQrCode`), `accessCount`, `lastAccessedAt` and `updatedAt`; an added exclusion requires an owner decision. Independently validate payment-method shape/scope and gate held payment/QR controls. Existing separate public QR storage is not certificate data. Payment-method/metrics-only changes do not reset private age or force ordinary-money projection.

### Client monetary content admission (corrected condition 6)

A client-created or client-rebuilt cache carries no certificate of its own. It is served only when its complete monetary envelope digest equals the private certificate for that token and protocol/state/shape, age and complete current source-input checks pass. Otherwise the server projects from the year and publishes a new certificate. With unchanged actual source inputs, a byte-identical rewrite is admitted as that certified content; the write event itself is not a refresh trigger. Client-persisted caches keep `moneyProjectionVersion: 1` exactly as server output does. No persistence exception or replacement binding is needed or authorized.

The client writer remains a release-interval and owner-preview parity artifact for upgraded clients. Decision A's one-projection/identical-cents requirement remains unchanged: served money always equals an envelope the server computed and certified under the current admission policy.

Required corrected-condition fixtures (G=$100, B=R=0, young certified available snapshot and unchanged actual canonical source inputs unless the fixture changes them):

1. Certified P=$100; stale client rewrites the byte-identical envelope with new `updatedAt`. Admission reuses P=$100, writes no new certificate and leaves private `projectedAt` unchanged. If source P has instead become $200 within the hour, the source digest changes: server-project and publish P=$200 even if the cache remains byte-identical P=$100.
2. Certified P=$100; source P becomes $200; client rebuild writes P=$200. Changed source/envelope forces server P=$200, balance −$100 and a new certificate.
3. Certified P=$100; source P becomes $200; stale client writes P=$50. Changed source/envelope forces server P=$200, never $50.
4. Certified P=$100; otherwise identical client envelope omits or changes `moneyProjectionVersion`. Incompatible shape forces fresh server projection and version 1 republication.
5. Payment-method-only and metrics-only updates preserve certified age/count behavior without projection for available money; held controls stay withheld, and certified unavailable still always reprojects.

## Exact transaction and response contract

1. After #676 the upgraded ShareView **never reads publicShares directly**, including retry/fallback paths; it renders only admission responses. Remove the raw cache read, separate client metric increment and `refreshOnly` together. Every committed admission increments once; callback retries add none. HTTP retries keep current non-idempotent behavior.
2. Read **exactly** live token, year, complete household notice query, cache and private certificate in one Admin transaction, all before writes. Source household/status/five arrays come from that year. Successful empty notice query is ready; failed/missing context is never empty. Internal notices are read regardless of detail scope; details remain token-member scoped, `refunds:read` only and live-only.
3. Validate live token, protocol/state/shape, source and payload digests and age, independently checking presentation scope/shape. Certified unavailable, missing/invalid certification, changed canonical source inputs or envelope mismatch, age over one hour, existing refunds:read live requirement or Try again forces a single fresh `projectHouseholdMoney` result over that snapshot. When source inputs changed, publish/serve that one fresh result whether available or unavailable, with a new certificate and new private `projectedAt`; never discard a valid result for old money or update only a memo. Never mix cached components into it. When unchanged available inputs and the rest of admission match within the hour, skip projection/certificate rewrite but retain the visit metric write.
4. Write **only** publicShares and shareCacheAdmissions, including the visit metric update in the cache. Never write token/year. Publish compatible available/unavailable, remove stale optional money, preserve existing cached counts rather than reseeding from token, and preserve actual token validity/scopes. No email/audit/HTTP/logging side effect occurs inside the callback. Await commit before response; read/commit exhaustion returns recoverable failure without stale fallback.
5. Unavailable withholds all money/pay/QR/question/progress/pending output while retaining independent scoped historical notices/actions and Review status/reply. After a successful report the same view starts an authoritative reread and rejects earlier response generations. Required sequence within one hour: hold → report → admission recertifies unavailable with reported history → ordinary invalid-amount correction → a new visit, without Try again, source-projects available money with reopened eligibility. The young unavailable certificate cannot be reused. Try again performs source reread, not year repair or a money-write retry.

A source transition committed first is observed or causes retry; a resolver committed first represents the earlier serializable snapshot. Network delivery can arrive after later events, hence component generation rejection. A changed/incompatible legacy replacement cannot certify itself. Concurrent admissions/legacy metric writes conflict on cache and retry; certificate/cache remain paired atomically. Existing payment-method sync preserves age/count behavior and cannot restore held controls.
